## 一、论文速览

## 论文名片

**论文标题：** ACM: Agentic Context Management for Long Horizon Tasks（面向长程任务的智能体上下文管理）

**论文网址：** https://arxiv.org/pdf/2607.23809

**作者团队：** Xiaochuan Li、Ryan Ming、Meng Chu、Shuai Shao、Rong Jin、Chenyan Xiong，作者来自卡内基梅隆大学（CMU）与 Meta。论文特别注明：实验、数据收集与处理均由 CMU 完成，Meta 主要承担顾问角色。

**发布时间：** 2026.07。

**核心关键词：** Agentic Context Management（智能体上下文管理）、Long-horizon Tasks（长程任务）、Context Compression（上下文压缩）、External Memory（外部记忆）、On-policy Distillation（在策略蒸馏）、Context Policy Learning（上下文策略学习）。

**一句话摘要：** 这篇论文不再把上下文压缩当成系统后台的一条固定规则，而是把“何时整理、整理什么、何时找回”变成 Agent 自己可以调用、可以学习的一组动作——让 AI 不只是拥有更长的记忆，还开始学会管理自己的注意力。

## 论文摘要（大白话版）

今天的 Agent 已经能搜索网页、阅读文档、调用工具、修改代码，甚至连续工作几十轮。但任务一长，它经常会出现一种很像人类“脑子塞满了”的状态：前面搜过什么忘了，失败路线又走一遍，真正关键的证据被埋在几十页工具输出里，最后不是答错，而是直接撞上上下文窗口上限。

传统解决办法通常有两种：一种是继续扩大上下文窗口，能塞多少先塞多少；另一种是在 Token 达到某个阈值后，强制把历史压成一份摘要。前者像把办公桌越换越大，却从不整理；后者像定时叫来保洁员，不管你是否正在用桌上的材料，都按时间把东西收走。

ACM 提出了第三种思路：给 Agent 配一套“工作记忆 + 长期档案库”。当前最重要的信息留在上下文里，暂时用不到的历史被摘要并归档，原始内容完整存到外部；未来某条旧线索重新变得重要时，Agent 再带着具体问题把相关细节找回来。

更关键的是，论文没有停留在“给模型两个工具”。研究者还设计了一套双约束后训练方法，专门教模型识别两类相反错误： **该整理的时候一直硬扛，以及不该整理的时候频繁乱压缩。**

因此，这篇论文真正研究的不是一个更聪明的摘要器，而是一个更深的问题： **Agent 能不能学会管理自己的上下文？**

## 二、破题：长任务 Agent 为什么越做越“糊涂”？

我们先想象一个真实场景：你让 Agent 调研一个冷门事实。它先搜索网页，再打开文档，接着排除几个错误候选，随后发现新线索，又换关键词继续搜索。几十轮之后，它的上下文里同时躺着搜索摘要、整页网页、失败尝试、工具报错、临时假设和已经过时的推理。

从表面看，这些都是“有用历史”；但对模型来说，历史越多不等于有效信息越多。真正的问题有三个。

- **容量压力：** 工具输出会快速消耗 Token。即使模型名义上支持几十万甚至上百万 Token，长轨迹依然可能触碰上限。
- **注意力稀释：** 关键线索与大量旧信息同时出现在工作区，模型需要反复从噪声里重新定位重点。
- **推理失焦：** 失败搜索和过期假设长期留在上下文里，会诱导 Agent 重复探索、绕圈，甚至在证据不足时提前作答。

所以，长上下文问题并不只是“装不下”，更是“放得乱”。更大的上下文窗口解决的是容量上限，却没有自动解决信息组织、注意力分配和证据回溯。

为了看清 ACM 到底改变了什么，可以把三种常见方案放在一起比较。

![Image](https://mmbiz.qpic.cn/sz_mmbiz_png/klUQVfPc8OyUyTZibU1NCjYZ1tRKKVoUOvUAiara6aFo7Rrwoib5oBUrEUtZhT1RDBZS1ey41OhvOcvBC0g0wfdgg3tAc8KhibH3AEib7dCInH5E/640?wx_fmt=png&from=appmsg&watermark=1#imgIndex=2)

**普通 ReAct** 会把完整历史一路带下去，直到任务结束或撞上窗口上限； **Summary Agent** 通常在上下文达到固定阈值时强制摘要，触发时间由外部规则决定，而且原始细节往往很难回查； **ACM Agent** 则让模型根据当前任务状态主动压缩，同时把原始消息保存到外部记忆，需要时再定向召回。

三者真正拉开差距的，不只是“有没有摘要”，而是两个更本质的问题： **压缩时机由谁判断？被移走的信息还能不能回来？**

## 三、核心方法与原理：给 Agent 装上一套“工作记忆系统”

ACM 的核心并不复杂。它借鉴了人类短期记忆与长期记忆的分工，只给 Agent 增加两个专用工具： `manage_context` 负责整理和归档， `query_memory` 负责按需查回原始内容。

## 工具一：manage\_context——不是删除历史，而是把材料归档

当 Agent 发现搜索开始重复、长工具输出不再需要常驻，或者一个阶段的证据已经基本收敛时，它可以主动调用 `manage_context` 。

系统会将上一个压缩边界之后的历史整理成一份新的工作记忆，同时把对应的原始消息写入外部存储，并为这段档案分配唯一的 `summary_id` 。此后，Agent 不必继续背着整段原始历史，只需要在当前上下文中保留一份更紧凑的“阶段笔记”。

论文要求摘要重点保留两类内容：

- **Knowledge state：** 已经确认的事实、候选答案、正反证据、被排除的方向、尚未解决的问题。
- **Thoughts：** 当前推理走到哪里、接下来准备做什么、还有哪些线索值得继续追。

摘要最长为 4096 Token，并特别要求日期、数字、实体名称和文档标识等关键信息尽量原样保留。换句话说，这不是普通的“帮我总结一下”，而是一份要支持后续行动的项目交接文档。

**大白话解释：**

它就像你在做一个持续几周的复杂项目。桌面上已经堆满了资料，与其把所有文件一直摊着，不如先写一份“目前确认了什么、排除了什么、下一步查什么”的阶段纪要，再把原件放进编号档案盒。桌面重新变干净，但资料并没有消失。

## 工具二：query\_memory——旧细节重新重要时，再去翻档案

压缩最大的风险是：今天看起来不重要的细节，明天可能突然成为关键证据。传统摘要很难在压缩发生时预知未来，因此无论提示词写得多细，都可能漏掉后续真正需要的信息。

ACM 的处理方式不是强求摘要“记住一切”，而是保留原文。当 Agent 后来需要核对某个日期、失败搜索、原始引用或早期候选时，它可以调用 `query_memory` ，同时提供 `summary_id + 具体问题` 。查询模型会读取对应的原始消息，只返回与当前问题相关的内容。

这相当于你不必把整本档案重新搬回桌上，只需要问档案管理员：“请帮我找出编号 07 的材料里，关于那家公司成立时间的原始证据。”

两个工具一收一放，形成了一套完整的记忆循环。

![Image](https://mmbiz.qpic.cn/sz_mmbiz_png/klUQVfPc8OyR7ejPXVOibRoWp5ZNQma1U9Jl1VoRePafJ6iaELvC90hJARBCTSmL3ic9icLftYXpU8IVEjkGOIBQLcO8XCS7RyibJ026DI0tNlXA/640?wx_fmt=png&from=appmsg&watermark=1#imgIndex=3)

这里必须澄清论文中“无损”的真实含义： **无损的不是摘要本身，而是被移出工作上下文的原始消息仍然被保存，并且未来可以重新查询。** 摘要依然可能遗漏信息，召回也依然可能不准确；ACM 的关键，是为被压缩的信息保留了一条可回溯路径。

## 四、真正难的不是提供工具，而是教会 Agent 何时使用

如果 ACM 只是增加了 `manage_context` 和 `query_memory` 两个函数，它的创新性其实很有限。真正困难的是：模型如何判断这一刻应该继续搜索、打开文档、召回旧证据、压缩上下文，还是直接给出答案？

这不是一道简单的 Token 阈值题。同样是 60K Token，Agent 可能正沿着一条有效线索快速推进，此时压缩会打断推理；也可能已经连续几轮搜索相似关键词，却没有获得任何新信息，此时继续堆历史只会放大噪声。

压缩太晚，Agent 可能陷入循环或撞上窗口上限；压缩太早，又可能把马上要用的证据移出注意力中心。所以， **上下文管理的本质不是“剩余容量判断”，而是“任务状态判断”。**

论文的行为分析还发现：把记忆工具写进 Prompt，并不意味着模型会主动使用。强模型往往很快解决简单任务，训练数据中缺少真正需要整理上下文的长轨迹；能力较弱的模型即使进入长轨迹，也未必能识别自己已经绕圈。于是就出现了一个尴尬局面：工具明明放在手边，Agent 却不知道什么时候该拿起来。

为了解决这个问题，研究团队设计了一套教师—学生双约束训练流程。

## 第一步：用 H− 和 H+ 两类轨迹，暴露相反错误

第一类轨迹记为 **H−** ：学生模型看不到 ACM 工具，只能像普通 ReAct 一样持续搜索和推理。这类轨迹容易暴露“该管理却没有管理”的错误，例如重复搜索、走进死胡同、积累了大量阶段性材料却迟迟不整理。

第二类轨迹记为 **H+** ：学生可以自由使用 ACM 工具。这类轨迹则会暴露另一个极端——“不该管理却管理了”。例如刚打开关键文档还没有深入阅读，就急着归档；或者证据已经充分，本应直接回答，却又做了一次多余压缩。

为什么正反两类数据必须同时存在？因为只教模型“什么时候要压缩”，很容易训练出一个频繁整理、却不推进任务的“压缩爱好者”；只教模型“不要乱压缩”，又会让它在上下文已经失控时继续硬扛。双约束真正学习的是两种动作之间的决策边界。

## 第二步：教师不只打分，而是在关键节点“改动作”

拿到两类轨迹后，教师模型会结合完整过程与参考答案，寻找真正影响后续结果的关键位置。

对于 H−，教师执行 **Injection（注入）** ：找出最早应该管理上下文的节点，把学生原来的动作替换为 `manage_context` 或相应的记忆操作。触发依据不是“窗口用了 80%”，而是轨迹里已经出现了重复查询、无效循环、阶段性知识收敛等结构性信号。

对于 H+，教师执行 **Refinement（纠正）** ：识别过早或多余的上下文管理调用，再把它换成更合适的动作——继续搜索补证据、打开文档深入阅读，或者在信息充分时直接提交答案。

这一设计的精妙之处在于，教师不是只说“这里错了”，而是明确告诉学生： **此刻更应该做什么。** 模型最终学到的不是一个孤立的压缩开关，而是在搜索、阅读、压缩、召回和作答之间做选择。

## 第三步：从修正点继续 Rollout，让正确动作产生完整后果

关键动作被替换之后，学生不会停在标注点，而是从教师修正后的动作继续完成任务。这样得到的数据不仅包含“正确动作是什么”，还包含这次动作会如何改变后续搜索、上下文规模与最终答案。

这一步很重要，因为上下文管理的价值往往要在十几轮之后才显现。一次及时压缩，可能让模型多探索二十轮；一次错误压缩，也可能让后续召回变得困难。只有把轨迹继续跑完，模型才能看到策略的长期后果。

## 第四步：难例筛选、防答案泄漏与 On-policy 蒸馏

研究者还增加了两层数据质量控制。首先，通过拒绝采样把训练重点放到真正困难、确实产生上下文压力的任务上；其次，检查教师说明是否泄露参考答案。教师可以指出“搜索正在重复”“证据已经足够”或“关键文档尚未深挖”，但不能借纠错之名把标准答案直接告诉学生。

训练阶段采用 On-policy Distillation。论文使用 Qwen3.5-9B 作为学生模型，Qwen3.5-397B-A17B 作为教师，为学生轨迹中的 Assistant Token 提供软概率分布，并保留 Top-20 候选 Token；系统提示、用户输入和工具输出不计入训练损失，整个后训练进行三个 Epoch。

![Image](https://mmbiz.qpic.cn/mmbiz_png/klUQVfPc8OzJrhVwWY9WkxMyia8ich4uj5liboNzskYqpdlcneTAKQUtRrMFGhL4T1ILhjbvic7ZCw8Z1uxHZ6Ky97MK7HlLCLThJ02iccL2YNUE/640?wx_fmt=png&from=appmsg&watermark=1#imgIndex=4)

论文的消融实验进一步说明，只蒸馏强教师的成功轨迹并不够。强教师可以传递通用解题能力，但专门构造的 H−/H+ 双约束数据，补上的才是“如何管理上下文”这项独立能力。

这给 Agent 工程一个很直接的启发：未来要训练的不只是“任务怎么完成”，还包括“内部资源怎么调度”。何时搜索、何时压缩、何时回忆、何时结束，本身都应该成为轨迹级能力，而不只是系统提示词里的一条建议。

## 五、实验结果：上下文变短了，Agent 反而走得更远

论文在三个长程任务基准上评测 ACM：BrowseComp-Plus 用于复杂深度检索，DeepSearchQA 强调开放网络搜索，SWE-Bench Verified 则测试真实代码仓库中的问题修复。

与 Qwen3.5-9B 的 ReAct 基线相比，ACM 后训练模型的 Pass@1 结果如下：

- **BrowseComp-Plus：** 从 0.570 提升到 0.727，相对提升约 27%。
- **DeepSearchQA：** 从 0.367 提升到 0.425，相对提升约 16%。
- **SWE-Bench Verified：** 从 0.489 提升到 0.530，相对提升约 8%。

但最值得注意的，不只是正确率提高，而是 Agent 的行为发生了变化。

论文分析发现，ACM 大约降低了 20% 的峰值 Token 压力，同时模型会调用更多搜索和文档工具，并完成更长的测试时探索。直觉上这有点反常：既然做了上下文压缩，为什么工具调用反而更多？

答案是，ACM 节省的不是“总工作量”，而是“工作记忆占用”。桌面被整理干净后，Agent 获得了继续探索的空间，能够把原本用于反复处理旧历史的注意力，重新投入到寻找新证据上。

论文给出了一个很有代表性的案例：Agent 整个任务一共走过约 222K Token 的原始轨迹，但实际工作上下文峰值被控制在约 98K，因此完成了 83 轮交互；如果不做压缩，它在第 47 轮就会越过 128K 的上下文上限。

**大白话解释：**

ACM 不是让 Agent “少想一点”，而是让它“少背一点”。它把暂时用不到的历史从桌面搬进档案柜，省下的空间继续用来查资料、验证假设和完成任务。

## 六、前路漫漫：ACM 也不是万能的“记忆外挂”

看到这里，你可能会觉得，只要给所有 Agent 装上 ACM，长任务问题就解决了。事情没有这么简单。论文的实验和局限性至少提醒了我们四个现实瓶颈。

## 瓶颈一：基础模型必须先有“走长路”的能力

ACM 只有在 Agent 真正进入长轨迹后才有价值。如果模型本身不会规划、不擅长使用工具，或者还没深入探索就提前猜答案，再先进的上下文管理也无从发挥。

论文在 Qwen3-4B-Thinking 上观察到，这个较小模型平均只运行约 2 轮、调用约 1.2 次搜索，还没有走到需要整理上下文的阶段就结束了任务。因此， **上下文管理是长程推理的放大器，不是基础推理能力的替代品。**

## 瓶颈二：原文可查，不等于一定查得准

ACM 保存了原始消息，但真正召回时仍然依赖 `summary_id` 、查询表达和查询模型。如果归档边界不合理、问题问得太宽，或者查询模型漏掉关键证据，Agent 依然可能“明明存过，却找不回来”。

所以企业落地时不能只评估压缩率，还要单独测量召回命中率、证据一致性、关键数字保真率，以及错误召回对后续推理的影响。

## 瓶颈三：每次整理和回忆都有额外成本

摘要要调用模型，查询长期记忆也要调用模型。压缩过于频繁，虽然工作上下文会变短，却可能增加总体延迟与推理成本；归档粒度太大，召回时又要重新读取大量原文。

因此，真实系统里需要平衡三件事：工作上下文峰值、额外模型调用成本，以及任务正确率。ACM 不是“压得越多越好”，而是要在正确时机做足够的整理。

## 瓶颈四：策略可能具有场景差异

深度搜索、代码修复、医疗报告解读和客服多轮对话，需要保留的信息并不相同。搜索任务更在意候选与证据，代码任务更在意文件路径、修改记录与测试结果，医疗场景还要求时间线、数值和证据来源不能丢失。

论文证明了 ACM 在所选搜索与编程基准上的有效性，但这不等于同一套摘要模板、训练数据和触发策略可以直接复制到所有行业。真正落地时，仍需为具体业务定义“什么必须常驻、什么可以归档、什么必须可追溯”。

## 七、创新价值：从 Context Engineering 走向 Context Policy Learning

这篇论文的创新价值，不只是多了两个记忆工具，而是把上下文管理从一套外部规则，推进为 Agent 可以学习的内部策略。

过去的 Prompt Engineering，关心的是“这一句话怎么写，模型才能答得更好”；Context Engineering 进一步关心“模型在这一刻应该看到哪些信息”；而 ACM 又向前走了一步： **能不能让 Agent 根据任务进度，主动决定哪些内容继续留在注意力中心，哪些暂时移出，以及何时重新取回？**

这可以称为 **Context Policy Learning（上下文策略学习）** 。上下文不再只是开发者在任务开始前拼好的一段静态输入，而是 Agent 执行过程中可以持续编辑、压缩、归档与召回的动态资源。

## 实际工程中应该怎么选？

并不是所有任务都需要直接上完整 ACM。可以按照下面的逻辑做选择。

![Image](https://mmbiz.qpic.cn/sz_mmbiz_png/klUQVfPc8OztspFbLjg8gt1HghibiayfT0ABHGhg7h8l4S7rWbkmHnHKvOQFAE3U6EJYBfSIvsuokK7XtZQNEroWmwRst192icMQMib6JV1zzHM/640?wx_fmt=png&from=appmsg&watermark=1#imgIndex=5)
- **短任务、少量工具调用：** 优先普通 ReAct。任务几轮内就能结束，没必要为记忆系统付出额外复杂度。
- **长任务，但流程稳定、预算有限：** 先使用“固定阈值 + 结构化摘要”，同时保留原始内容，为未来回查留下基础。
- **多轮探索、工具输出很长、旧证据可能重新重要：** 使用 `manage_context + query_memory` ，让工作记忆与长期记忆真正分层。
- **场景稳定、已有高质量轨迹和后训练能力：** 再进一步训练上下文策略，让模型学习压缩与召回的准确时机。

工程上还可以采用“学习策略 + 硬护栏”的混合方案：平时由 Agent 主动判断，Token 接近危险阈值时由系统强制兜底。这里需要说明，这属于基于论文机制的工程推导，并不是论文已经直接验证的配置。

如果把这条演进路线画出来，它会非常像一套逐步成形的 Agent“上下文操作系统”。

![Image](https://mmbiz.qpic.cn/mmbiz_png/klUQVfPc8Ox137MGz2VFHfWdg1pa9KbqV6sSbrymzR1JZ8xuJGJA7STJLK7gSZcAdomaeaFIiarK2Y06X6A93z6W0pnkrK9d6ctZTwS6PCfw/640?wx_fmt=png&from=appmsg&watermark=1#imgIndex=6)

工作上下文像高速但有限的内存，外部存储像容量更大的磁盘， `manage_context` 负责换出， `query_memory` 负责换入，而上下文策略决定什么时候执行这些动作。

优秀的 Agent 不是永远把所有内容都放在眼前，而是知道： **此刻什么最值得占据注意力中心。**

## 八、总结：真正强大的 Agent，不是记住一切，而是管理一切

ACM 像一份写给长任务 Agent 的“记忆管理手册”。

- **它告诉我们：** 长上下文的核心矛盾不只是窗口不够大，而是工具输出、失败轨迹与关键证据混在一起，最终让注意力失焦。
- **它提供了：** `manage_context` 与 `query_memory` 两个动作，让 Agent 可以整理工作记忆、保存原始档案，并在新问题出现时重新找回细节。
- **它真正推进的是：** 用 H−/H+ 双约束轨迹教会模型判断时机——该整理时别硬扛，不该整理时别瞎压缩。
- **它也提醒我们：** 上下文管理不是基础能力的替代品，召回、成本、数据质量和场景适配仍然决定着系统能否真正落地。

过去，我们总在问模型的上下文窗口还能扩大多少。ACM 把问题换了一个方向：当窗口里已经拥有足够多的信息，Agent 是否知道该把注意力放在哪里？

这也是它对 Agent 工程化最重要的启发：未来系统竞争的重点，不只是模型参数、窗口长度和工具数量，还包括 Agent 对自己内部资源的调度能力。

**更长的上下文窗口，只是给 Agent 一张更大的桌子；真正的智能，是它终于学会了整理桌面，保存档案，并在正确的时刻找回那张关键纸条。**
